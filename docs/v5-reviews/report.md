# Go Teacher report format 5 — specification (revised, final)

Scope: `src/report.rs` (Markdown), a new `src/evidence.rs` (the structured evidence built from `GameAnalysis`), `src/report_html.rs` (viewer tweaks), small changes to `src/teaching.rs` (restricted atari list feeds the theme rule) and `src/analysis.rs` (a `probes` field), and the contract the skill parser must implement. Analysis-side algorithms (pass probe, moves-ownership, restricted L&D search, variation tree, realistic refutation, replays, rank estimate) are owned by the analysis spec; this document fixes **what the report shows, in which shape, with which field names, signs and units**, and states every assumption about those computations that the report depends on, so both specs line up. Where a value is assumed rather than fixed by the analysis spec it is marked "assumed".

Grounding measurements (format 4, 94-move 9x9 game, `~/Documents/GoTeacher/20260914_191026_*.md`): 66,087 bytes = Game information 0.9 KB, How to read 4.0 KB, Summary 5.0 KB, Teaching candidates 15.0 KB, Game arc facts 2.0 KB, Move-by-move 33.5 KB (51%), Final position 0.6 KB, Appendix 5.0 KB. The brief `parsed.json` the LLM reads today carries `move_details` for every move, so for a 250-move game the agent-facing payload is ~90–110 KB, most of it not about the lesson. Facts from that game used below: move 43 Black A5 (loss 33.1, KataGo's #17 of 17 searched, net prior <0.1% ranked #14 of 81), best J5 (B+33.9), score before B+33.8, after B+0.7, opponent's last move 42 White A4 (loss 34.3), actual reply 44 White A2 (loss 8.1 → B+8.8), engine refutation B1 A2 H4 J4 J3 J5 H1 D9 → B+0.6, unrestricted atari list after the move: Black F8 (2 stones), White A4 (3 stones); Black's winrate flips 0.2% ↔ 99.8% at moves 31/32 and 0.5% ↔ 99.9% at 41/42; `phase_of(59, 94)` = middlegame.

## 0. Design principles

1. **One source of truth.** `src/evidence.rs`: `pub fn build(a: &GameAnalysis) -> Evidence`. The Markdown is rendered *from `Evidence`* and the *same struct* is serialised into the trailing ` ```json ` block and to `<stem>.evidence.json`. The two views cannot disagree.
2. **Fixed shape per lesson.** Every lesson has every row/bullet in the same order; unavailable facts print `—` (Markdown) / `null` (JSON).
3. **Facts, not prose.** The format-4 free-text `hints` disappear. The only generated sentence per lesson is a templated headline.
4. **One word and one sign per fact.** Every point value the LLM might compare is printed from the **student's view with positive = cost/loss** (Loss, Loss vs best, Plan difference "given up", delta vs before is the exception: it is a signed change and is always labelled with the colour). The same event never has two polarities (`punished: no` in the Missed-opportunities table is `Punished? no` in the lesson row).
5. **Numbers the LLM would otherwise have to compute are precomputed** (delta vs the position before the lesson move after every sequence, `played_vs_pass`, `human_lets_off`, `stayed_lost`).
6. **Less bulk.** No move-by-move section, no one-line entries, no checkpoint diagrams, no opponent-mistake entries unless they are missed opportunities. Targets for a 250-move 19x19 game: Markdown ≈ 140 KB *including* a ≈ 55 KB JSON block; the default agent-facing `parsed.json` ≈ 25–30 KB (tested, section 12.6).
7. **No arrays of ownership or policy anywhere in the report.** Ownership is reduced to regions and groups; policy to probabilities of named moves. Ownership-derived numbers say *where*, never *how much*: they are rounded to whole points in Markdown and footnoted as approximate.

## 1. Section order (format 5)

```
# Go game review: <title>
Generated by go_teacher using <engine> on <date>.
Report format: 5

## Game information             metadata table (+ profiles, probe budget, evidence size)
## How to read this document    ≤ 16 one-line bullets (section 7)
## Student profile              NEW: rank estimate per phase, time discipline, trend vs earlier games
## Summary                      shrunk (section 3)
## Lessons                      overview table + one evidence pack per lesson + "### Praise"
## Missed opportunities         NEW: opponent mistakes and whether the student kept the gain
## Game arc facts               unchanged table + "### Life-and-death changes"
## Opening patterns             unchanged (13x13+ only)
## Key positions                REPLACES "Move-by-move analysis": format-4 full entries for lesson moves,
                                compact entries for missed-opportunity replies, the final position
## Appendix: compact move list  unchanged (+ optional time column)
## Evidence (JSON)              NEW, last: one fenced json block with the whole Evidence struct
```

Removed vs format 4: `## Move-by-move analysis` (all one-line entries, checkpoint entries and diagrams, the opponent's mistake entries), `### Point loss by phase`, `### Time and loss`, the opponent's `### Biggest mistakes` table, `## Final position` as its own section (folded into Key positions), `## Compared with the student's earlier games` as its own section (folded into Student profile), the hint bullets.

### 1.1 Game information (`| Field | Value |`)

Rows in order: Black, White, Result recorded in SGF, Date, Event, Place, Board size, Handicap, Komi used for analysis, Rules used for analysis, Time settings, Number of moves, Student, Analysis strength, Deeply re-analysed positions (two-pass only), **Human profiles** (`student rank_20k (chosen at upload); target rank_15k; opponent rank_10k (from SGF rank "10k"); mode asymmetric`), **Probe queries** (`412 queries (of which 288 replay plies), 531 s: pass value, local life and death, variation trees, realistic refutations, replays, rank estimate`), Analysis wall time, **Evidence JSON** (`51,204 bytes, section "Evidence (JSON)"`). Player names are sanitised: strip Unicode control, zero-width, Hangul-filler (`ㅤ`, U+200B occur in the sample) and `|` characters.

**SGF rank → profile mapping** (`opponent_source`): strip non-alphanumerics, match `^(\d+)([kdp])` case-insensitively; `k` → clamp 1..20 → `rank_{n}k`; `d` → clamp 1..9 → `rank_{n}d`; `p` → `rank_9d`; no match → assume the student's profile with `opponent_source: "unparseable_sgf_rank"`; no rank → `"assumed_same_as_student"`; user override → `"user"`.

**Profile mode** (assumed, analysis spec): main passes run with the asymmetric profile `rank_{BR}_{WR}` (Black rank first; the student's or target's profile in the student's colour slot, the opponent profile in the other), so each colour's `humanPolicy` is at its own rank from one pass (verified for `rank_10k_3k`; verify a dan form such as `rank_20k_1d` with a live query — if rejected, fall back to symmetric profiles plus one extra 1-visit pass over the opponent's turns and the probe positions at the opponent profile, `TurnEval.human_policy_opponent`, `mode: "symmetric_plus_opponent_pass"`). When the opponent profile equals the student's, the symmetric name is used (`mode: "symmetric"`).

Definitions (values also in JSON `student`):

- **Rank estimate input** (assumed, analysis spec): profiles tested `rank_20k, rank_18k, rank_16k, rank_14k, rank_12k, rank_10k, rank_8k, rank_6k, rank_4k, rank_2k, rank_1d, rank_3d, rank_5d` (13, uniformly ~2 ranks apart; all exist per the brief's list `rank_20k..rank_1k`, `rank_1d..rank_9d` — confirm each with one live query before shipping). One 1-visit query per profile over the student's turns only (`analyzeTurns` = positions where the student is to move, excluding passes and the last two moves): ~0.1 s per position → 13 × 47 ≈ 60 s on the 9x9 sample, 13 × 125 ≈ 160 s for a 250-move game. Per move k and profile π: `l_π(k) = ln max(p_π(move_k), 1e-3)` (floor 1e-3 caps outlier influence; ln(1e-3) = −6.9). Per phase (and whole game): `L_π = mean_k l_π(k)`.
- **best** = argmax L_π. For every other profile π: `d_k = l_best(k) − l_π(k)`, `t_π = mean(d) / (sd(d)/√n)` (sd with n−1; if sd = 0, t = +∞). Self-calibrating: no labelled corpus needed to know whether a difference is noise.
- **range** = the span from the lowest to the highest profile (in list order) among {best} ∪ {π : t_π < 1.0}; JSON keeps both ends and the per-profile `t`.
- **margin_t** = min t_π over profiles at least 2 list steps from best (both directions). **confidence**: `low` if n < 15 or margin_t < 1.0; `high` if n ≥ 40 and margin_t ≥ 2.5; else `moderate`. Section 12.4 validates the ordinal labels against declared ranks.
- **Rendering**: profile tokens print as human words via a fixed map (`rank_12k` → `12 kyu`, `rank_1d` → `1 dan`); when confidence is `low` the "Played most like" and "Indistinguishable from" cells print `—` and the confidence cell `low (too few moves)` / `low (profiles too close)` (values stay in JSON). The 9x9/13x13 caveat sentence prints when `board.x < 13`.
- **Time discipline**: computed over the **student's** timed moves only (`time.basis: "student_moves"`, requires ≥ 8; opponent bots move in ~1 s and would drag a shared median to nothing). One definition of fast everywhere: `fast = time ≤ student median`. `big_losses_fast` = the student's 8 biggest losses (by point_loss) with time ≤ median. Verdict `fast_moves_cost_more` if fast mean loss ≥ 1.25 × slow mean loss and big_losses_fast ≥ 4 (of 8; if fewer than 8 losses exist, ≥ half); `slow_moves_cost_more` if slow mean ≥ 1.25 × fast mean and big_losses_fast ≤ 8 − 4; else `no_pattern`. Losses are `max(point_loss, 0)`.
- **Trend** (≥ 2 earlier games): `improving` if this game's mean loss ≤ recent average − 0.3, `worse` if ≥ +0.3, else `flat` (0.3 pts/move ≈ search noise on a mean over 100+ moves).

Edge cases: no human model → "No human-style model was loaded, so there is no rank estimate." and `rank_estimate: null`; < 15 student moves in the whole game → only the whole-game row, confidence low; no clocks → Time discipline omitted, `time: null`; < 2 earlier games → comparison omitted, `trend: null`; a phase with 0 student moves → row omitted.

## 3. Summary section (shrunk)

Kept, in order:
1. Opening sentence (start/end estimate, recorded result) — unchanged.
2. `### Accuracy by player` — unchanged table.
3. `### Game flow` — every 10 moves + last, with the bar — unchanged.
4. `### Biggest mistakes by the student` — student's table only, max 8 rows, loss ≥ 1.5, format-4 columns.
5. `### Turning points` — then one line about decidedness.

**Turning points** (fixes the band bug): include every move where the lead changed hands, `(wr_before − 0.5) × (wr_after − 0.5) < 0` and `|Δwr| ≥ 0.05`, **regardless of the band**; plus every move with `|Δwr| ≥ 0.15` whose `wr_before` is inside 5–95%. Cap at 6 by `|Δwr|`, then `|Δscore|`. Line format unchanged from format 4 (`- Move N (Colour MV): Black winrate a% → b%, score S1 → S2 — the lead changed hands.`).

**decided_from** = the smallest turn index N (position after move N, 0 = start) such that for every turn t ≥ N the winrate is on the **same side** of the band (all ≥ 0.95 or all ≤ 0.05); `null` if the final position is inside 5–95%. Line: `The game was decided from move 42 onward: after move 42 Black's winrate stayed above 95%.` / `The game was still open at the end of the record.` On the sample this gives 42 (not 7, which the old rule produced while the lead still changed hands four times). Unit test: sequence `[0.98, 0.02, 0.99, 0.01, 0.99, 0.99]` (turn 0..5) → `decided_from = 4` (last flip at turn 3 → 4 onward same side) and exactly 3 lead changes among the turning points. `Lesson.decided_before` keeps its format-4 meaning (winrate before the move outside 5–95%) but the overview column header reads `Decided (Black wr before)` and the Lessons header restores the clause "Winrates in the table are Black's".

Recommendation rule (`recommended: true` on up to 3 lessons; computed from pass-1/2 data before probes so replays can be limited to ★ lessons): `score = min(loss, 20) × (decided_before ? 0.7 : 1.0) × (1 + human_prob_student_of_played/100) × (difficulty == "very hard" ? 0.7 : 1.0)`; greedy by score with distinct themes, repeats allowed if fewer than 3 themes exist. Reasoning: the cap stops one 40-point blunder dominating; decided positions teach less about winning; a typical mistake (high human policy) generalises; "very hard" moves are poor first lessons. The skill may override.

Theme change in `teaching.rs`: the `Theme::Reading` rule ("own group in atari after the move") uses the **restricted** atari list of Facts row 9 (groups within the locality radius of the played stone or the opponent's last move), computed once in `build()` and shared. On the sample this turns move 43 from "reading / tactics" (Black F8, 5 points away, in atari for unrelated reasons) into "over-defending / priority" (A5 answers A4 locally while J5 elsewhere is worth 22+ points), which is the correct lesson.

Element-by-element definitions:

**Headline.** Template: `{Colour} played **{MV}** ({loss} points lost, {category}; KataGo's #{r} of {searched} searched moves | not searched by KataGo) where KataGo prefers **{BEST}** ({best_score} instead of {played_score}). Theme: {theme}. Phase: {phase}. {The game was already decided (Black {wr}% before the move): judge by points, not winrate. | The game was still open (Black {wr}% before the move).}` — `r` = 1-based search rank (`MoveReview.rank + 1`), `searched` = number of moveInfos in the deep search of P, `played_score` = root score of turns[i+1]. When best == pass: `where KataGo prefers **to pass** (…)`.

**Facts table** (17 rows, always present):

1. *Value vs passing (urgency)*: `value_vs_pass = sign_student × (score(best candidate in P) − score(P + [student pass]))`, from the pass probe (≥ 300 visits, assumed). Labels: ≥ 15 `huge`, 8–15 `large`, 4–8 `medium`, 1.5–4 `small`, < 1.5 `tiny` (size words; "urgent" is reserved for the threat flag, so "urgent before big" stays meaningful). **threat** (boolean): in the pass-probe root ownership (position after the student's pass, the opponent's expected best play already priced in) some student group of ≥ 2 stones goes from alive/unsettled in P to dead (±0.4 rule), or the pass-probe top reply is adjacent to a student group with ≤ 2 liberties. Row text: `{v} pts, {label}[, threat] — {BEST} is worth this much more than passing[; passing would let {Opp} {reply} ({kills|ataris} {group})]`. Go note: value vs pass lies between the miai and deiri values of the biggest move (approaches deiri in a settled position, tempo/miai with many moves left); quote it rounded to whole points, ignore differences under 1 pt (search noise ±0.5–1 at 300 visits). Edge cases: opponent's previous move was a pass → probe skipped, row `— (the opponent had just passed)`, `urgency: null` (verify by live query whether KataGo returns a result for a two-pass position; record in the brief; `run_query_ext` bails on any `error`, so skipping is mandatory until verified). Best == pass → `0 — the best move was to pass`, `value_vs_pass: 0`, `label: "tiny"`.
2. *Compared with passing*: `played_vs_pass = value_vs_pass − point_loss`. `≥ 0`: `{MV} kept {played_vs_pass} of the {value_vs_pass} points available`; `< 0`: `{MV} was {|x|} pts worse than a pass`. `—` when urgency is null.
3. *Reply to the played move*: from the opponent's candidate list in turns[i+1] (deep). `best_reply` = the candidate with the best score **for the opponent** among candidates with visits ≥ 5 (not visit order); `reply_distance` = Chebyshev distance to the played move; `local_reply_share` = visits of replies within the **locality radius R** ÷ visits of all listed replies. **R = 2 on boards ≤ 13x13, 3 on larger boards** (a distance-3 square covers 49 of 81 points on 9x9). Kind: `punishment` when point_loss ≥ 3.0 or the reply captures stones / puts the played stone's group in atari (checked on `Board`); else `answer`. Text for `punishment`: `{Opp}'s best reply {X} is {d} away from {MV} ({share}% of the search local) — {punished locally | the punishment comes from elsewhere}` (locally if d ≤ R). Text for `answer`: the sente/gote verdict as in row 4. A pass as best reply → `{Opp} would ignore it (pass)`; verdict gote.
4. *Reply to the better move*: from the variation-tree search of P+best (300 visits): same fields; verdict `sente` if reply_distance ≤ R and share ≥ 0.6, `gote` if reply_distance > R and share < 0.4, else `unclear`; `kind: "answer"`. Text: `{verdict} — {Opp}'s best reply to {BEST} is {X}, {adjacent | d away} ({share}% local)`. Best == pass → `—`, `sente.preferred = null`. How-to-read carries the caveat that "sente" means "the engine expects a local answer".
5. *Difficulty*: `close_candidates` = candidates in P within 1.0 pt of the best (mover's view, visits ≥ 5), including the best; printed as `no other move within 1 pt of {BEST}` / `{n−1} other moves within 1 pt`. `best_policy` = net prior of the best; `best_human_prob_student/_target` = human policy of the best at the two profiles. Label from the student-profile probability p: ≥ 30% `easy`, 10–30% `medium`, 3–10% `hard`, < 3% `very hard`; one step easier if close_candidates ≥ 3. Without a human model (`basis: "engine"`): cuts on `best_policy` ≥ 60 / 30–60 / 10–30 / < 10 and the row says `(engine policy, not human)`.
6. *Endgame values*: only when phase = endgame or value_vs_pass < 4 (an endgame-type decision); else `—`. **Derived, no query**: for the best, the 2nd/3rd candidates and the played move, `value_vs_pass(c) = value_vs_pass(best) − loss_vs_best(c)`, each with the reply verdict from its tree root when available: `J3 4.1 (gote), H2 3.8 (sente), C8 0.4 (gote)`. Note (in How-to-read): values are comparable across candidates; a sente move keeps the turn afterwards, which the engine's scores already include.
7. *Where the points went*: as today (`loss_region`, `loss_region_points`), whole points.
8. *Better move is*: `same area (dist d)` if d ≤ 2, else `elsewhere (dist d)`; `—` if best is pass.
9. *Answers the last move?*: `played: yes/no; better: yes/no (opponent's last move X)` with the format-4 radius 2; if the opponent's last move is a pass or absent: `n/a (no previous move to answer)`, JSON `played/preferred: null`.
10. *Stone captured?*: `yes, move N` (within 10 moves) / `no`.
11. *In atari after the move (within R of MV or the opponent's last move)*: the restricted list; `none`. Header carries the radius.
12. *Time spent*: `N s (fastest quarter | slowest quarter | )` (quartiles over the student's timed moves) / `—`.
13. *Policy*: `net prior {p}, ranked #{k} of {board points + 1} points` (policy rank counts pass).
14. *Human policy ({student profile})*: `{p} (#{k}); most common move {X} ({q}%)`.
15. *Human policy ({target profile})*: same; `—` without a target.
16. *Punished?*: only when the opponent's previous move lost ≥ 4.0 (else `—`). Tier by `reply_loss / opponent_loss`: ≤ 0.25 `yes (kept the gain)`, ≤ 0.60 `partly (kept part of it)`, else `no (gave the gain back)`. Text: `{tier} — {Opp}'s move {N−1} {X} lost {G} pts; the student's reply lost {l} ({tier words}). Punishment line: {best PV ≤ 6} → {score} ({delta})`. Same value and words as the Missed-opportunities table; JSON `punished: "yes"|"partly"|"no"`.
17. *Only move missed*: `yes — {BEST} was {gap} pts better than the next candidate {X}` when `gap = sign × (score(best) − score(second)) ≥ 1.5` (second's visits ≥ 5) and the student did not play the best (the praise rule uses 2.0; 1.5 here so the row fires on the sample's 1.5-pt gap — anything ≥ 1.5 is a "clearly better" move by the category scale); else `no`.

Footnote line (fixed text, after the table): `Ownership-based rows (Where the points went, Plan difference, group statuses) say *where*; they are approximate and do not add up to the point loss. Quote the point loss for *how much*.`

**Position line** — byte-compatible with format 4 (`- Position before the move (...)`); stones sorted top-left → bottom-right; setup stones included.

**Local frame line** — `- Local frame (zoom for the lesson board; stones the explanation may cite): columns {a}–{b}, rows {m}–{n}; Black ...; White ....` Consumer: (a) the lesson page shows it as a zoomed view of the real board (`view: {cols, rows}`; `generate_lesson.py` crops the canvas), no coordinate translation; (b) with the L&D probe's key moves it forms a sanctioned `from_game: true` exercise type that the validator exempts from the identical-position check while still checking legality. Fresh puzzles remain the skill's own transformed positions. Construction: bounding box of points within Chebyshev 3 of the played and better moves, clipped to the board, expanded to ≥ 5×5; then **extended to include every stone of any group intersecting the box** (recompute; groups still cut when the extension would exceed 11×11 are listed in `groups_cut`); if played and better are > 8 apart, two frames (`around A5` / `around J5`). On boards ≤ 9x9 the frame is the whole board (`whole board (9x9)`, `cols/rows` = full range, stone lists omitted in Markdown, present in JSON).

**Plan difference line** — `own_played` = **always** `turns[i+1].ownership` (root after the played move, deep; the played candidate's `includeMovesOwnership` map has 1–10 visits for a blunder and is a near-raw-net guess); `own_best` = the best candidate's moves-ownership map if its visits ≥ 100, else the root ownership of the P+best search the variation tree runs anyway. `cost_region = sign_student × Σ_{p∈region} (own_best[p] − own_played[p])` — **positive = points the student gives up** by playing MV instead of BEST. Print regions with |cost| ≥ 1.5, largest first, max 4, whole points, then `total {T} given up`. Groups: every group in P with ≥ 2 stones (plus single stones in atari), mean ownership under each map → ±0.4 status; print groups whose status differs (`alive with A5, dead with J5`), max 4, largest first — **only when both maps have ≥ 100 visits**, else `groups: not compared (too few visits)`. Trailer `(ownership at {visits_played} / {visits_best} visits)`. If no region reaches 1.5: `no region differs by 1.5 points or more; total {T} given up`.

**Local life and death lines** — one per probed group (max 2), then a closing line. Group selection (assumed shared): groups of ≥ 2 stones, or any group in atari, within Chebyshev 2 of the played or better move, with |mean own| < 0.7 in P or appearing in this move's `status_changes`; ordered by stone count. Window = empty points within distance 2 of the group plus `pass`, capped at 30 nearest. Two restricted searches (`allowMoves` same list both players, `untilDepth` 8, ~300 visits, assumed): *defender first* on P if the group is the student's (else on P + [student pass]); *attacker first* on the other. Status after the top restricted move = mean of that candidate's moves-ownership over the group's stones → ±0.4 rule (alive / dead / unsettled). **Full verdict table**: defend=alive & attack=dead → `unsettled — whoever plays first decides`; alive & alive → `alive locally`; dead & dead → `dead locally`; defend=dead & attack=alive → `unknown (probe inconsistent)`; any pair containing `unsettled` → `unclear locally (ko or seki likely)` with both raw statuses printed and both key moves null. Top restricted move `pass`: defend-first → `no move needed`, status alive, move null; attack-first → `no attack found`, status alive, move null. Top candidate visits < 30 → verdict `unknown`. Then two booleans in words: `{MV} is inside/outside this fight` (in window), `{BEST} is / is not the key move` (equals saving/killing move). **No scores from restricted searches are printed anywhere.** Liberties from `Board::groups`. Closing line: `no other group within 2 points of {MV} or {BEST} needed a probe` / `no group within 2 points of the move needed a probe`.

**Candidates table** (new, 6 rows: top `top_moves` = 5 from P + the played row): `| Move | Score | Loss vs best | Visits | Net policy | {student profile} plays it | {target profile} plays it |`. The played row uses `turns[i+1]` root score and visits, labelled `(played)`. This is what the skill's "alternatives" panel consumes; Key positions keep the format-4 table for humans.

**Sequence bullets** — one grammar for every bullet, for the fallback parser:
`- {Label} ({params}): {moves} → {score} ({Colour} {±x} vs before move {N})[; {clause}[; {clause}]]`
where `params` is free text that always starts with `{Colour} first`, `score` is `B+x`/`W+x`, the delta is the change of the **student's** score relative to the root score of P (ASCII `+`/`-`, one decimal, colour named). Regex: `^- ([^(]+?) \((Black|White) first[^)]*\): ((?:[A-T]\d+|pass)(?: (?:[A-T]\d+|pass))*(?: \.\.\.)?) → ([BW]\+[\d.]+) \((Black|White) ([+-][\d.]+) vs before move (\d+)\)(?:; (.*))?$`. `Actually played` prefixes the move with its number (`44 A2 (loss 8.1)`) — its regex variant allows `\d+ ` and `\(loss [\d.-]+\)` before the arrow.
- *Better line*: best candidate's PV in P (≤ 8), score = that candidate's score.
- *Engine refutation*: `best_reply` of turns[i+1] (best for the opponent, visits ≥ 5) + its PV (≤ 8), its score.
- *Realistic refutation* (`after {MV}, as {profile}`): the opponent's human-style reply at the **opponent's** profile: `argmax over moveInfos of humanPrior × exp(utility_opp / 0.5)`, deterministic; cross-check against the `humanPolicy` array's top legal move — if that move is not in moveInfos and has ≥ 2× the chosen move's probability, use it instead (`source: "human_top_unsearched"`). Then P+played+reply analysed at ~300 visits: line = reply + its PV (≤ 7), score = its root score. Clauses: `a {profile} {Colour} finds {engine refutation first move} {p}% of the time`; `the {profile} reply costs {Student} {realistic cost} instead of {engine cost}` (`human_lets_off = engine_delta − realistic_delta`, printed as the two costs). If equal to the engine reply: print the engine line again with the clause `same as the engine refutation, found {p}% of the time`.
- *Actually played*: `{N+1} {X} (loss {l}) → {score after N+1} (delta)`; absent when the lesson move is the last move (`—`).
- *Replays* — **four fixed labels for ★ lessons, all `null` for others** (JSON `replays: []`), sharing start positions pairwise so the UI toggle maps 1:1 onto {student, target} × {played, better}: `as_played_student` (start P+played), `as_played_target` (P+played, student side at the target profile), `preferred_student` (P+best), `preferred_target` (P+best). Params: `{Opp/Student} first, after {MV|BEST}; Black {profile}, White {profile}, {plies} plies`. `Replay.moves` **excludes** the lesson move (starts at the first replayed ply); the Markdown prints them as-is (the panel places the lesson move itself). Clauses: `ranged {min} to {max} during the replay` (from the ~20-visit per-ply evaluations, `score_min/max`); `ends after move {N+plies}` or `ended early: two passes after move {M}`; on `preferred_student` only: `of the {loss} points lost, about {stayed} stayed lost at student level` where `stayed = round(sign × (end_preferred_student − end_as_played_student))`, printed only if |stayed| ≥ the noise threshold (5 pts on ≤ 13x13, 8 pts on 19x19, to be set by 12.8); if stayed > loss: `the gap grew to about {stayed} points`; if stayed < −threshold: `the loss was recovered`; otherwise `whether the loss stayed is unclear`. Same for `preferred_target` vs `as_played_target` (`at target level`). Per-ply move selection (assumed): the deterministic human-like rule at ~20 visits; stop at two consecutive passes; 24 plies. `status_events` come **only** from the 500-visit start and end evaluations (groups ≥ 2 stones, from → to), never per ply. A fixed caveat bullet follows the replays: `Replays are one plausible continuation each, not predictions; differences under {threshold} points between replays mean nothing on this board.`

**Variation tree table** — columns `Line from the position | Score | Loss vs best | Visits | Note`. Nodes (assumed): roots = top 3 candidates of P plus the played move if not among them (≤ 4); root scores from P's deep candidate list (`source: "candidate"`), except the played root = turns[i+1] root (`source: "root"`, visits = root visits). Children: from a 300-visit search of P+root (P+played uses turns[i+1]): the engine reply (best for the opponent, visits ≥ 5) for every root; additionally the opponent-profile human reply for the best and the played root (merged when equal); the realistic-refutation node carries its own search (`source: "root"`). ≤ 10 rows. `Loss vs best = sign_student × (score(best root) − score(node))`. Note ∈ {`better move`, `played, position after it`, `2nd candidate`, `3rd candidate`, `engine reply, from the search after {root}`, `engine refutation, from the search after {root}`, `{profile} reply ({p}%), own search`, `engine reply = {profile} reply ({p}%), from the search after {root}`}. How-to-read states: Visits = how much search the line got; under 50 treat the score as rough; "Loss vs best" is relative to the best candidate, the headline point loss relative to the root evaluation — they differ by a few tenths.

**Chain line** — unchanged from format 4. **Status changes line** — `- Status changes caused by this move: ...` / `none.`

Expected size per pack: 3.0–4.0 KB on 9x9, 3.6–4.8 KB on 19x19 (stone lists dominate); ★ lessons add ≈ 0.9 KB of replays.

## 7. "How to read this document" (≤ 16 bullets, one line each)

1. Coordinates: GTP, columns A–T without I, rows from the bottom; `pass` is a pass.
2. Winrates are always Black's; scores are `B+x`/`W+x`; point losses, values and "given up" numbers are from the student's view, positive = cost; categories best < 0.5, good < 1.5, inaccuracy < 3, mistake < 6, big mistake < 12, blunder ≥ 12.
3. Start with **Lessons**: same evidence block each; `—` = not available; ★ = the program's three suggested lessons (you may pick others with a reason).
4. **Value vs passing** = how much the best move is worth compared with passing (between the miai and deiri value of the biggest move); whole points, ignore differences under 1; **threat** means passing would cost a group. **Compared with passing** says whether the played move was better or worse than doing nothing.
5. **Reply to the played/better move**: whether KataGo's best reply is local (within 2 points on boards up to 13x13, 3 on larger) — for the better move this is sente (local answer expected, ≥ 60% of the search) or gote; for a blunder it only says where the punishment comes from.
6. **Difficulty** combines how many moves were nearly as good with how often players of the student's rank find the best move; the row shows the numbers behind the label.
7. **Plan difference** = where the expected territory differs between the played and the better move, by region and group; numbers are points the student gives up by playing the move (positive = worse). Ownership-based rows say *where*, not *how much*.
8. **Local life and death** comes from a search restricted to the points around a group: statuses and key moves only — never quote scores for it. "Unsettled" = whoever plays first decides.
9. Sequences: *Better line*, *Engine refutation*, *Realistic refutation* (the reply a player of the opponent's rank most likely finds), *Actually played*, and four *Replays* (both sides continue as human players of the stated ranks; ★ lessons only). Every line says who moves first and, after the arrow, how the student's score changed versus the position before the lesson move.
10. A **replay** is one plausible continuation, not a prediction; differences under the stated threshold between replays mean nothing.
11. The **variation tree** and **candidates table** evaluate lines from the lesson position; `Loss vs best` is from the student's view; Visits = how much search the line got (under 50 = rough).
12. **Human policy** rows give how often players at the student's and target ranks play the move and what they play instead.
13. The **Student profile** rank estimate is style similarity, not a rating — quote it with its range and confidence, never alone, and not at all when confidence is low.
14. **Punished?** compares what the opponent's mistake offered with what the student kept; **Praise** lists only moves that were the only good move in a live position.
15. **Game arc facts** and **Life-and-death changes** are the only sources for "a group died / was saved / was captured"; **Key positions** hold candidate tables and diagrams for the lesson moves; the **Appendix** lists every move.
16. **Evidence (JSON)** at the end contains all of the above as one JSON object; a parser should read it first and use the Markdown only as a fallback.

## 11. Cost and edge cases

Probe budget the report prints (owned by the analysis spec; listed so `AnalysisInfo.probe_*` and the visit annotations agree). Per lesson (8): pass probe 1 query (≈ 3 s at 300 visits), L&D 2–4 restricted (≈ 3 s each), variation tree 3 searches (P+best, P+2nd, P+3rd; P+played is turns[i+1]) ≈ 3 s each, realistic refutation 1 (≈ 3 s) → 7–9 queries, ≈ 25–30 s → ≈ 4 min for 8 lessons. Replays, ★ lessons only: 4 × (24 plies × ≈ 0.3 s at 20 visits + one 500-visit end evaluation ≈ 5 s) ≈ 50 s per lesson → ≈ 2.5 min. Rank estimate 13 one-visit queries over the student's turns: ≈ 60 s (9x9 sample), ≈ 160 s (250-move game). Opponent-profile fallback pass ≈ 12 s. **Total ≈ 6–7 min on the 9x9 sample, ≈ 9–10 min on a 250-move 19x19 game, on top of pass 1 + pass 2**; query count ≈ 70 + 288 replay plies + 13 ≈ 370, printed as `N queries (of which M replay plies)`. If the analysis spec trims, the pack shape does not change — fields become `null`. Probes use `priority` to overtake a long pass-1 query when jobs interleave.

Edge cases the renderer must handle: no human model (all human/profile fields null, Student profile says so, Difficulty `basis: "engine"`, realistic refutation and replays null); no target profile (`human_policy.target = null`, `*_target` replays null, candidates column `—`); opponent rank absent/unparseable (assumed = student, source printed); played move unsearched (`rank_in_search: null`, headline "not searched by KataGo", tree root from turns[i+1]); best == pass (urgency 0, better_move_is null, frames around the played move only, `reply.preferred = null`); opponent's previous move a pass (urgency null; answers_last null/n/a); pass as best reply (gote / "would ignore it"); groups larger than the window cap (nearest 30, count printed); inconsistent probes (`unknown`), ko/seki (`unclear`), top restricted move pass ("no move needed"/"no attack found"), < 30 visits (`unknown`); replay reaching two passes (`ended_early`); lesson on the last move (`actual_reply: null`, replays from P+played still run); game shorter than 20 moves (profile rows "too few moves"; missing phases omitted as today); handicap/setup stones (in stone lists and diagrams); rectangular boards (3×3 region names; frame clips to `size_x/size_y`); names with control characters (sanitised); zero lessons (`No move by the student lost 1.5 points or more.`, `lessons: []`, Key positions = final position only); no missed opportunities (`No opponent move lost 4 points or more.`); opponent mistake on the last move (row with `not answered (end of record)`).

## 12. Empirical checks before trusting the labels

1. **Value vs pass**: a settled 9x9 endgame with one remaining 4-point deiri gote move → ≈ 4; with independent 4/3/2-point gote moves left → ≈ 2–3 (tempo). Confirms the "between miai and deiri" wording. Also run a two-pass position (opponent passed, student passes) and record whether KataGo answers; until confirmed the probe is skipped.
2. **Reply locality**: an atari on a 3-stone group → local (distance 1, share > 0.9); a first-line monkey jump vs a big open-area move → gote. Validate the 0.6/0.4 shares on 10 hand-made positions **each** on 9x9 (R = 2) and 19x19 (R = 3); check that for 5 known blunders the `punishment` kind fires and no `sente` label is printed.
3. **Local L&D**: second-line groups with both ends open — 6 stones `dead locally`, 8 `alive locally`, 7 `unsettled`; a 2-stone group in atari with a working ladder → `dead` under attack-first; a seki → `unclear`; a group already alive → defend-first top move `pass` → "no move needed". Verifies the window (distance 2), the ±0.4 rule and the 3×3 verdict table.
4. **Rank estimate**: confirm all 13 profile names with one live query each; 10–20 OGS/KGS games with declared ranks: the whole-game `best` within ±3 ranks of the declared rank in ≥ 70% of games, and `high` confidence right ≥ 85% of the time (adjust the 1.0/2.5 t cuts only if this fails); a 9x9 sanity run on the KaTrain sample games (the estimate should not swing more than ±4 ranks between phases of the same game) before the row is shown for boards < 13x13 — if it fails, print the section note "not reliable on this board size" and keep `rank_estimate` in JSON only.
5. **Realistic refutation**: on the KaTrain 9x9 sample the rank-profile opponent's chosen replies should match the actual "Human-like" bot replies often; report the match rate (move 44 A2 is the check case).
6. **Size and round-trip** (`cargo test`): render a synthetic 250-move analysis with 8 populated lessons (3 ★ with four replays each) and assert the JSON block ≤ 96 KB, the whole report ≤ 200 KB, the default-trimmed `parsed.json` ≤ 32 KB; the fake-engine pipeline test asserts `Report format: 5`, all 11 section headings, `serde_json::from_str::<Evidence>` round-trips the fence, and exercises: pass-as-top-restricted-move, opponent-pass-before-lesson (urgency null), best == pass, unsearched played move, missed opportunity on the last move.
